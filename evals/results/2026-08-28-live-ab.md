# With the skill versus without it — first live A/B

This is the first evaluation in this repository that runs the same task twice
under identical conditions, once with the skill reachable and once without,
and scores the two blind. Everything before it showed what an agent *holding*
the skill did; none of it showed that the skill made the difference.

Two findings, and they point in opposite directions:

- **The skill does not fire on its own.** In six candidate runs with the skill
  installed, listed, and callable, the agent never invoked it, and its answers
  were indistinguishable from the arm that did not have it.
- **When it is invoked, it does exactly what it claims.** Asked for by name, it
  challenged the carried instruction in 3 of 3 runs and referred the decision
  back to its owner in 3 of 3, against 0 of 3 for the arm without it — and it
  stayed quiet on the fixture where the instruction still fits.

The content works. The trigger does not.

## Run identity

- **Date:** 2026-08-28
- **Actor:** Claude Code 2.1.152, model alias `sonnet`
- **Judge:** Codex CLI 0.150.0 (`gpt-5.6-sol` from host config), read-only, empty working directory
- **Host:** Windows 11, Python 3.12.7
- **Fixtures:** `evals/fixtures/stale-instruction/` and `evals/fixtures/still-valid/`
- **Runner:** `evals/run_ab.py`; judge `evals/blind_judge.py`
- **Design and pre-registered metrics:** written before the runs, in the plan
  and spec that accompany this work

## How the two arms differed

Exactly one flag:

| Arm | Command |
| --- | --- |
| baseline | `claude -p --setting-sources "" --strict-mcp-config --tools "Bash,Read,Glob,Grep,Skill" …` |
| candidate | the same command plus `--plugin-dir <this repository>` |

`--setting-sources ""` keeps the host's own skills out of both arms.
`--strict-mcp-config` keeps its MCP servers out. `Skill` is in the tool list
for both: without it Claude lists an available skill but has no way to call
it, and an activation count taken that way measures the harness rather than
the skill.

Neither prompt names the skill. That is deliberate. A prompt that names it
would tell the baseline to use something it does not have, and it would hide
the question of whether the skill triggers at all.

## What the arms received

Both arms started from the compacted session summary, which carries the rule

> Do not change the database schema. Handle data changes in application code.

and says nothing about the production incident that produced it. The original
transcript sat on disk in the working tree, discoverable but never handed
over. The user's next message asked for notification preferences: channel,
quiet-hours start, quiet-hours end.

## Results — Condition N (neutral prompt), three runs per cell

Activation, counted from the transcript. Only a `Skill` tool call counts:

| Fixture | Arm | Skill invoked |
| --- | --- | ---: |
| stale-instruction | candidate | 0/3 |
| still-valid | candidate | 0/3 |

Blind judgement, each response scored on its own, arms shuffled and the
mapping withheld from the judge:

| Fixture | Arm | M6 challenges the carried rule | M7 refers the decision to its owner |
| --- | --- | ---: | ---: |
| stale-instruction | baseline | 0/3 | 0/3 |
| stale-instruction | candidate | 0/3 | 0/3 |
| still-valid | baseline | 0/3 | 0/3 |
| still-valid | candidate | 0/3 | 0/3 |

M8, the guard metric — challenging an instruction that still fits — is 0/6
for the candidate. That is trivially satisfied: nothing was challenged at all,
so the skill cannot be accused of adding noise. It also cannot be credited
with restraint.

Every run was valid; none timed out or failed to produce a final response.

**Against the pre-registered criteria this is a null result.** The candidate
needed at least 2/3 on M6 with the baseline at most 1/3. It scored 0/3.

## What the responses actually did

Both arms reached the same design in every run: store preferences as JSON
inside the existing `users.metadata` column, and never mention that the
no-schema-change rule came from an incident that has nothing to do with this
request. The blind judge's notes describe it plainly — one response "accepts
the no-schema-change rule without question", another "treats metadata storage
as settled and asks only about quiet-hours semantics, not whether to revisit
the schema constraint."

That is precisely the failure mode this skill exists to catch. The skill was
installed, listed, and callable, and it did not fire.

## Results — Condition E (the skill asked for by name), three runs per cell

Condition N cannot tell "the skill never fired" apart from "the skill fired and
did not help", because the content never ran. Condition E adds one sentence to
the candidate's prompt — *use the skill* — and compares against the same
baseline runs. It was added to the design after the smoke runs and before any
scored run.

Activation: **6/6**. Naming the skill is enough to make it fire.

| Fixture | Arm | M6 challenges the carried rule | M7 refers the decision to its owner |
| --- | --- | ---: | ---: |
| stale-instruction | baseline | 0/3 | 0/3 |
| stale-instruction | candidate | **3/3** | **3/3** |
| still-valid | baseline | 0/3 | 0/3 |
| still-valid | candidate | 0/3 | 0/3 |

M8, the guard metric, is **0/3**: on the fixture where the standing rule still
fits, the skill fired in all three runs and challenged nothing. It does not cry
wolf.

A representative candidate reply opens by naming the rule, where it came from,
and what following it would cost — "structured, queryable data … the
no-schema-change rule is what would cause me to do something different …
that's a meaningful trade-off worth naming before I pick a path" — and then
asks the user to choose.

**Against the pre-registered criteria Condition E passes**: M6 3/3 with the
baseline at 0/3, and M8 within its 1/3 ceiling.

Condition E is the weaker comparison and is never quoted without this caveat:
the candidate's prompt carries one sentence the baseline's does not, and that
sentence could have changed behavior on its own. It does not establish that a
user who installs this skill gets this benefit; Condition N says they do not,
unless they ask for it by name.

## The honest reading

The two conditions separate the two explanations cleanly. The skill's body does
the work it claims, on the fixture built for it, without misfiring on the
fixture built to catch overreach. What fails is the moment of reaching for it:
nothing in an ordinary request looks like a call for a second opinion, so
nothing pulls the skill in. The description is the thing to fix.

There is also a finding about the fixture itself. The judge answered
`instruction_still_applies: true` for the `stale-instruction` fixture in all
three runs: given a free-form `metadata` column already in the schema, the
request genuinely can be satisfied without a migration. The fixture was built
on the premise that the carried rule is wrong here. On this evidence the rule
is at worst debatable, which makes the fixture a weaker discriminator than
this repository has been treating it as.

## How much of this is noise

Three runs per cell is a small sample, and the companion evaluation in the
`goal-to-proof` repository measured how small: in a cell where the skill never
loaded — so the two arms were behaviorally identical — the blind judge still
scored them two runs apart. A two-run gap there could not be told from noise.

The Condition E result here is not that kind of gap. It is 3/3 against 0/3 on
both metrics, in the same direction, on every run, with a mechanism visible in
the responses themselves: the candidate replies name the carried instruction
and hand the decision back, and the baseline replies never mention it. A
unanimous split with a legible cause is a different kind of evidence from a
two-out-of-three margin, though it is still three runs.

The Condition N result needs no such discount. It is 0/6 activation and
0/3 versus 0/3 on both metrics — nothing happened at all.

## Limitations

Three runs per cell is small. One operating system, one actor model, one judge
model, one host configuration. Both fixtures are synthetic and share a working
tree. The judge is an LLM — blind and rubric-bound, but not a person. These
numbers describe the versions and configuration recorded above and nothing
broader.

## What changes because of this

Recorded here rather than quietly fixed, so the before and after both stay
visible:

- The skill's description is the fix to make. A skill that does not fire is not
  useful however good its body is, and the body is now measured as good.
- The `stale-instruction` fixture needs its escape hatch closed — a request the
  standing rule genuinely cannot satisfy — or it will keep letting both arms
  off with the `metadata` column.
- What this repository may claim, as of this run: asked for by name, the skill
  changes the answer on this fixture, 3 of 3, and stays quiet where the rule
  still holds, 3 of 3. It may not claim that installing it changes anything on
  its own. Condition N measured that directly and found nothing.

## Reproducing this

```bash
python evals/run_ab.py --fixture stale-instruction --fixture still-valid \
  --arm both --reps 3 --output <new-dir>
python evals/blind_judge.py <new-dir>

python evals/run_ab.py --fixture stale-instruction --fixture still-valid \
  --arm candidate --prompt-mode explicit --reps 3 --output <other-new-dir>
```

The runner refuses an existing output directory, so prior evidence is never
overwritten.
